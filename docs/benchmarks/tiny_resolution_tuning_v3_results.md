# Tiny640 跟踪参数搜索 v3 结果

## 未找到满足全部无回退条件的配置

2026年9月5日，固定Tiny640检测结果与原ByteTrack，对MOT17 calibration执行27组有限搜索。
执行和原始基线复现通过，但26组改动配置均出现MOTA回退；没有配置满足
[v3冻结筛选规则](tiny_resolution_tuning_v3.md)的全部条件。因此不指定最终参数，不切换默认
Tiny416，不把最高HOTA当作整体质量验收。原25W质量FAIL和CSI成对验证限制保持不变。

[完整CSV](tiny_resolution_tuning_v3.csv)包含每组四段及官方COMBINED共135行，保留五阈值、
HOTA/DetA/AssA/IDF1/MOTA、Recall/Precision、TP/FP/FN、IDSW、Frag和小目标诊断。
[证据索引](tiny_resolution_tuning_v3_evidence.json)记录配置、源码/输入/程序哈希及未验证项。
这次是缓存检测上的主机跟踪调参，不是新的Jetson性能、CAVIAR事件F1或holdout结果。

## 基线重放与统计口径

固定MOT17-02/04/05/10-FRCNN，共3141帧，按原协议处理85894个有效人物GT观测；原图框高度
h<100的15891个GT观测单列。每个配置仍用相同的GT、忽略区域和TrackEval匹配规则。
Recall是跟踪输出的官方CLEAR召回，不是原始检测框召回；小目标中断沿用既有诊断定义，
不等同于官方Frag或IDSW。小目标诊断保留绝对计数，不能由“中断变少”直接推断同一批轨迹更连续。

Tiny416/Tiny640各四份缓存以原阈值重放，8份MOT输出与板端原文件字节一致；Tiny640原配置的
四段及COMBINED十二项官方指标也复现一致。原ByteTracker、第三方跟踪代码与MOT写出源码
SHA均保持原值，TrackEval固定为`12c8791b303e0a0b50f753af204249e622d0281a`。
COMBINED由官方指标各自的combine_sequences计算，不是四段百分数的简单平均。

score=0.10、NMS=0.45、buffer=30固定；搜索track={0.25,0.30,0.35}、new-track={0.35,0.40,0.45}、
match={0.70,0.75,0.80}。缓存来自原25W engine推理、已做人物类别筛选和NMS，不能恢复更低score
检测或重新改变NMS。这次没有改变检测器阈值、重新推理、修改模型或操作设备。

0.30/0.45/0.75是减少误报和身份切换的取舍示例：HOTA提高0.879、IDF1提高1.092，FP减少610、
IDSW减少44、Frag减少55，小目标中断194→167。但Recall下降1.038个百分点、MOTA下降0.277，
小目标匹配观测2482→2360（召回15.619%→14.851%），说明部分“中断减少”同时伴随覆盖减少。

Recall下降0.249个百分点，MOTA下降0.112，小目标召回下降0.170个百分点。这也是需要接受
权衡后才可继续验证的候选，不把很小的IDSW变化夸大为稳定性突破。

## 逐序列和共同覆盖限制仍需保留

完整CSV保留四段分项，不以整体改善隐去某个序列的回退。原同阈值Tiny416/Tiny640
[共同/新增覆盖诊断](tiny_resolution_development_v2_results.md)原样保留；本轮只复算各组
原高度分组匹配及绝对中断，尚未为取舍配置重新计算共同轨迹的中断时长和连续跟踪时长。
因此不能把某组更低的总中断解释为相同轨迹上的连续跟踪改善。新的同GT配对诊断应在继续
验证的参数范围确定后补齐。

## 性能矩阵尚未执行，默认项保持不变

后续应以最终冻结的同一套参数构建Tiny640独立矩阵：720p/1080p、25W原时钟/MAXN_SUPER锁频、
MP4V/x264共8种候选工况；Tiny416使用x264作相同输入/功率对照。720p MAXN_SUPER是主要
30FPS目标，1080p和25W是补充；计时窗口、预热、输出完整性与硬件保护阶段采样见v3协议。
这些新行当前全部NOT_RUN，不能用主机重放耗时或旧Nano矩阵填入。

既有Tiny640 [CSI带事件短测](tiny_resolution_csi_event_retest.md)为原参数的MAXN_SUPER结果：
30.006253 FPS、TRT P95 7.090735ms、E2E P95 11.502294ms，正常丢帧和序列缺口为0。
这不是调参后的测量，也不证明60分钟稳定性、事件F1或充足余量。旧OC3窗口计数增加1的
阶段归因问题仍未解决；此前动作不一致的配对限制不因本轮调参而消失。

下一步先明确是否接受某个取舍配置及对应质量容差；不在看过结果后自动放宽v3门槛或追加网格。
随后最多选择已明确的少量配置，补齐同GT连续性诊断与板端重放一致性，再在三段固定CAVIAR
开发视频上比较逐类事件Precision/Recall/F1。配置确定后才执行性能矩阵与至少60分钟持续运行。
不运行holdout，不修改systemd、默认engine或README默认命令。
