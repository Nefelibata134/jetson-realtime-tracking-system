# Tiny640 开发验证协议 v2

## 目标与历史边界

本协议单独检查 Tiny640 在 MAXN_SUPER + `jetson_clocks` 下的 CSI 1280×720 完整链路
实时可行性，再决定是否进入 CAVIAR development。720p/30 是主要目标；25W 不再是这份
开发协议的强制达标配置，1080p/30 仅为可选增强。默认 Tiny416、25W 服务建议和 systemd
不变。30 FPS 不代表有充足余量，更不自动授权默认切换。

[原25W同阈值协议](tiny_resolution_protocol.md)、[原始结果](tiny_resolution_results.md)
及小目标中断75→194的 FAIL 原样保留。v2允许独立继续实时性开发检查，不重算旧门槛、
不把旧FAIL改为PASS，也不是新独立外部测试。所有 holdout 禁止读取、运行或调参使用。

机器可读配方为
[`tiny_resolution_development_v2.json`](../../configs/benchmarks/tiny_resolution_development_v2.json)。
配方、执行器、二进制和engine在设备执行前做SHA-256冻结；结果写入全新且不可复用的目录。
只有两组均完成、恢复和证据复核通过后才给出比较结论。

## CSI首轮固定配方

- 复用同一目标Jetson上已验证的Tiny416与Tiny640 FP16 engine；不重建、不改模型或ByteTrack。
- 两组均为MAXN_SUPER模式2、相同CPU/GPU/EMC锁频条件；固定先416后640。
- IMX219 sensor 0 / mode 4，1280×720/60采集，经现有`videorate`向应用交付1280×720/30。
  60→30是设计中的帧率转换，不冒充采集队列丢帧；不能据应用序列完整性证明传感器零丢帧。
- 每组先处理300个预热帧，再测量3600帧，目标测量时间120秒，单组硬超时240秒。
  不因结果接近门槛而延长预热、截掉慢窗口、补帧或换一组计时。
- 输入队列2、标注视频队列4，均保留有界丢旧策略。阈值与原同阈值calibration完全一致：
  score/NMS/track/new-track/match=`0.10/0.45/0.30/0.40/0.80`，buffer30。
- person class 0；归一化ROI=`0.25 0.20 0.75 0.90`；有限竖线=`0.50 0.20 0.50 0.90`，
  双方向；停留3秒。事件锚点沿用现有实现。两组使用相同相机位置、照明、区域与动作顺序。
- 事件JSONL、JPEG截图、前1秒/后1秒片段、x264标注视频（10000kbps）、最终metrics全部开启。
  保留现有片段编码器，不静默替换编码实现；异步队列、编码耗时与停止flush单独报告。
- 逐测量帧日志开启；外部接收器保存单调时钟时间及原文，遥测500ms。日志记录成本计入
  吞吐；E2E延迟沿用运行时的输出提交边界，不包含随后stdout写出。

## 真实人物与输出核验

每组执行前确认真实人物与相机均就绪，不在停服状态下无限等待。完成预热后，在约20秒内
从画面侧边进入、穿越中线、在ROI内停留至少5秒、再穿线离开，重复六轮。禁止用静态图片、
空场景或其他视频替代CSI输入；两组动作尽量重复，但不假装两次现场活动逐帧相同。

标注视频须人工复核确有人员活动与动作覆盖，JSONL至少包含入口入侵、穿线、停留三类
真实事件，各类至少1次；检查对应截图/片段可解码且与事件相符。没有事件或输出缺失的
轮次不得称为“带事件完整链路PASS”。人工复核前状态为REVIEW_REQUIRED，不自动放行。
这不是带独立真值的事件Precision/Recall/F1评估，事件数量不能代替后续CAVIAR质量。

## 固定统计边界与可行性判定

1. 有效FPS沿用运行时`measured_frames / elapsed_seconds`：从首个测量帧进入检测前，到
   最后一帧处理循环退出；不含预热、模型加载及停止flush。另报告实际耗时，不四舍五入后判定。
2. 固定将逐帧接收日志分成六个600帧窗口，窗口FPS为`599/(末条接收时间−首条接收时间)`。
   这是约20秒的外部日志观察窗口，会受管道调度影响；只作稳定性诊断，不替换运行时主FPS。
   报告所有窗口及最差值，不筛选窗口。短测不声称满足60分钟稳定性要求。
3. 预热300帧的丢弃单列`warmup_dropped_frames`；测量丢弃使用运行时差分，不从总数中
   任意剔除。测量帧日志必须完整、序列严格递增且零缺口，无无效帧、流重连或跟踪重置。
4. E2E从应用帧采集时间戳至同步事件I/O及标注视频提交完成；不是传感器曝光到文件落盘。
   TRT P95含现有TensorRT同步/拷贝边界。预处理、后处理、ByteTrack、事件分析、全部事件I/O、
   活跃事件I/O、视频enqueue与各自样本数分别报告；不得相加或平均P95。
5. 暂定实时可行性须满足未舍入有效FPS≥30、E2E P95≤33.33ms、测量采集丢弃0、序列缺口0、
   标注视频丢弃0、3600/3600帧写出且可解码、`target_reached=true`，并完成真实事件证据复核。
   任一失败保留FAIL；不能因主FPS达标掩盖编码积压、窗口抖动或尾延迟。
6. 记录CPU/GPU、系统RAM、进程RSS、输入功率、CPU/GPU/结温、CPU/GPU/EMC实际频率与锁频
   约束。持续遥测覆盖加载/预热/测量/flush，整机汇总不可标成模型独占。可用热节流计数器
   前后差分、内核热/过流记录一并保留；不可访问或缺少计数器标为不可用。频率下降只作
   线索，不能无证据归因为温控；温度达85°C主动中止，系统原有温控保持开启。

## 同批GT轨迹连续性诊断

只复算既有四段calibration预测，不重新推理、不调参。锁定旧GT、seqinfo、预测与TrackEval
提交哈希，继续采用官方有效GT、忽略目标预处理和CLEAR IoU0.5全帧匹配。以原始GT身份
连接两模型结果，不能把重新编号的预测身份跨模型关联。

- 全体有效GT轨迹固定不变；小目标子集为至少有一个原图高度<100px有效观测的GT轨迹。
  同时报告该子集全寿命与只看<100px观测两种覆盖率，不能只保留能被检测的GT。
- 按是否至少匹配一次分为双方共同覆盖、仅Tiny640覆盖、仅Tiny416覆盖、双方均未覆盖。
  全寿命分组和<100px观测分组分别计算；这些是事后描述性分组，不能当作无选择偏差的因果分层。
- 覆盖率=匹配观测/同一GT有效观测；同时保留逐轨迹、微平均、宏平均、GT数和观测分母。
- 原定义的匹配→漏配→重新匹配中断计数保留，另记录每次漏配帧数/秒、总时长、P50/P95/
  最大值。GT自身缺席切断片段；初始漏配和末尾未恢复分别列为删失，不悄悄忽略。
- 连续跟踪时长分别报告连续有匹配与连续保持同一预测身份的区段，身份变化必须切断后者；
  每段帧数除以该序列原帧率（05为14，其余30），同时保留最长段/逐段分布。
- 保留官方HOTA/DetA/AssA/IDF1/MOTA/Recall/Precision/IDSW/Frag/TP/FP/FN以及原75→194
  小目标中断与所有回退。归一化指标只解释暴露差异，不代替绝对量或改写旧FAIL。

## 条件后续与恢复

CSI短测可行后才进入固定CAVIAR development（Walk1、Browse1、EnterExitCrossingPaths1front），
逐类记录入口入侵/穿线/停留TP/FP/FN与Precision/Recall/F1。当前配方不授权任何阈值搜索；
如需调参，先另行冻结有限范围、运行预算与选择标准，再产生新目录，保留同阈值结果。
新配置必须重新验证相同最终engine的质量与实时性。最终候选至少60分钟持续运行，固定
人物活动时段、全程输出/计数/遥测，并避免只用最后延迟环形窗口代表整个小时。

停服前保存设备/BSP/软件、Git、服务PID/实际Tiny416 engine、部署文件哈希、真实帧增长、
原功率及CPU/GPU/EMC/idle/风扇/热策略；调用`jetson_clocks --store`写入独立新文件。
仅临时停止默认服务、切换已存在模式2并锁频，不改systemd或任何配置文件。
失败、超时、SIGINT/SIGTERM/SIGHUP均终止本轮拥有的进程后尝试恢复已保存时钟、原功率，
再启动Tiny416并验证active/running、NRestarts=0、实际engine和新增真实帧持续递增。
恢复结果与测试结果分开，不用测试失败掩盖恢复失败。

若模式切换要求重启、依赖/BSP/功率配置文件变更，立即停止并恢复，不回答重启确认。
断电或SIGKILL无法保证进程内恢复，保留原状态和恢复命令供核验；不改sudoers、不读取密码。
无论PASS/FAIL均保留日志及所有原始输出；本协议不授权提交、推送、默认切换或holdout。
